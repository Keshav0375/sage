### 2. Feasibility facts

WRONG (conditionally) M1 as written for partitioned tables. PostgreSQL 16 docs, ddl-partitioning "Limitations": "There is no way to create an exclusion constraint spanning the whole partitioned table. It is only possible to put such a constraint on each leaf partition individually." PG17 release notes add exclusion constraints on partitioned tables (partition-key columns must be compared with equality). So on PG16, `EXCLUDE USING gist` declared on a `PARTITION BY LIST (tenant_id)` parent errors. P-reliability puts the constraint on `document_versions`; ADR-003 partitions only `chunks`, so it works if `document_versions` stays unpartitioned. It cannot be put on `chunks`, and the brief's check item 3 ("chunk key + daterange + tstzrange with LIST partitions") is not satisfiable on the parent. Workaround: per-leaf constraint created by the same `migrate` step that creates each tenant partition (LIST by tenant makes cross-partition exclusion moot). Add this to the onboarding ticket and to the L0 check "every tenant partition has the constraint".
HOLDS-WITH-NOTE (M1) constraint shape. As written it is only valid-time exclusion on rows whose sys_range is open (`WHERE upper_inf(sys_range)`), not the textbook (valid && sys) bitemporal constraint (P-learning's form, needs PG18 spike). That is fine, but the ADR must say historical sys_range rows are not constrained. `ON CONFLICT DO UPDATE` cannot arbitrate on an exclusion constraint (PG docs), so upserts must use the separate unique key. Constraint checks bypass RLS (key includes tenant_id, so no cross-tenant signal).
HOLDS Kafka. Confluent topic docs (docs.confluent.io/cloud/current/topics/manage.html, 2026-11-02): retention.ms default 7 d, editable, min/max not stated for Basic; segment.ms editable, minimum 4 h enforced (so 1 d is valid; this resolves P-reliability's UNVERIFIED); max.compaction.lag.ms minimum 7 d on Basic/Standard/Enterprise. The 7 d min applies to compaction only; delete-policy topics never use it, so "retention 7 d" and "compaction lag min 7 d" do not conflict. Window = segment.ms 1 d + retention 7 d, about 8 d. Retention.ms upper bound on Basic still not found.
HOLDS BigQuery `max_time_travel_hours = 48`: docs say window "from a minimum of two days to a maximum of seven days"; fail-safe "an additional seven days after the time travel window", "isn't configurable". 2 + 7 = 9 d. CAVEAT: this is a per-dataset setting (the docs page does not name the field; the BigQuery API/DDL option `max_time_travel_hours` accepts multiples of 24 from 48 to 168, from memory, not re-read), so every dataset (including dbt/Dagster-created ones) must set it or the window is 14 d; no control in the design asserts this.
HOLDS Cloud SQL automated backup retention 7: docs give a range 1 day to 10 years (one troubleshooting entry says count 1-365); instance deletion rolls backups off one per day matching the retention setting. PITR transaction-log retention range was not on the pages I could read: still UNVERIFIED (known community figure 1-7 d on Enterprise; confirm).

### 3. M3 / M4 claims

UNSUPPORTED "weekly canary drill measures real windows". The BigQuery fail-safe is, per the BigQuery docs, not queryable and not user-observable (only Customer Care can recover it); the P-reliability probe at T+9 d (`FOR SYSTEM_TIME AS OF` rejected) only proves the 2-day time-travel window closed. The 9 d figure stays a documented number, not a measured one. PITR log retention and Anthropic/Voyage retention are also unobservable. The canary also cannot be "maximum of last 12" until 12 weeks have passed, and a BQ/Kafka window needs 9-14 days before the receipt closes.
UNSUPPORTED SLA "trace store within 24 h": Langfuse says "usually within 15 minutes", no guarantee, no confirmation (ev §2.3); the design alerts at 24 h, i.e. the SLA is exceeded by design when Langfuse lags.
CORRECTED M3 "backups <= 7 d" holds only while the instance is running its automated backup schedule. A stopped Cloud SQL instance (demo-on-demand) takes no new backups; whether old backups still expire on schedule while stopped is not documented. Test it.

## Correctness holes (task 2): scenario, why it breaks, missing control

H1 Tombstone cache defeats the race control (delete during ingest, replay, Kafka lag). R4 says sinks cache tombstones for 60 s and the silver worker re-checks after writing Parquet. With a 60 s cache the post-write check can miss a tombstone committed 1-59 s earlier: erased bytes survive in silver/BigQuery/GCS. A resurrected BigQuery row also restarts the 9-day time-travel + fail-safe window, so the M3 "<= 14 d" bound breaks silently. Missing: write-guarding checks must be uncached point reads inside the sink's own transaction/write path (cache only for the "should I even consume" fast path); erasure steps re-sweep each store at T + cache TTL + max consumer lag and again at the end of each store window; the resurrect alarm must restart the receipt clock.
H2 ACL tightening during a Kafka outage (the M2 gap). ADR-022 routes both ACL changes and `DELETE /v1/admin/documents/{id}` through `acl_change_requests` + outbox + `acl.changes.v1` + acl-applier. M2 moves the deletion queue to Postgres but P-reliability leaves acl-applier on Kafka. During a Kafka outage a tier/jurisdiction downgrade or a doc re-classification is not applied; the old ACL keeps serving (P-simplicity moved the applier to table polling for exactly this reason). Also M2 needs an explicit ADR-022 amendment, since doc delete now has two paths. Missing: acl-applier polls `acl_change_requests` with SKIP LOCKED; Kafka event kept for analytics only; test "stop Kafka, tighten ACL, answer is refused within 60 s".
H3 Parser-bump replay is a no-op or a duplicate generator. R2 idempotency: "same bytes seen twice = no-op"; same version_key with different bytes = silent_edit. A reprocess with a new `parser_version` (same bytes) is neither. If forced through, old and new parses of the same version have the same valid_range, both survive (no chunk-level exclusion), so `valid_range @> as_of` returns both parses (duplicate/stale chunks) until someone deletes the old ones. Test #8 ("replay twice, hash equals single run") never exercises the old-parse to new-parse transition. P-simplicity's single `reconcile_lineage` (one tx diff keyed by chunk_hash + valid_from) covers it. Missing: parser_version in chunk identity with an atomic swap in the publish tx, plus a test "bump parser, replay, no chunk of the old parse is retrievable".
H4 Chunk identity cannot represent a re-appearing provision. Identity is unique on (tenant, doc, provision_path, chunk_hash, embed_model) with ONE `valid_range` per row and "same hash => extend". Text A (2018), B (2020), A again (2023: a reinstated or reverted provision; eCFR and UK revocation/reinstatement exist) needs two disjoint intervals for the same key. Result: unique violation, or a wrong extension [2018, inf) that answers 2021 questions with A. Missing: datemultirange for chunk validity or valid_from in the key (P-simplicity includes valid_from); a property test with permuted version sequences including reversion (test #11 permutes order, not reversion).
H5 Tombstone scope and permanence. `erasure_ledger` stores `salted_hash(subject or doc id)` with no `tenant_id` in the row definition. If tombstones are not tenant-scoped, erasing Firm A's copy of a document blocks Firm B's ingest or replay of the same doc ("duplicate document in two firms"). Permanent tombstones also block legitimate re-ingest (FCA module revoked then reinstated; a firm re-uploads a document it deleted by mistake; EDGAR filing removed then refiled). Missing: tombstone key (tenant_id, doc_key, sha256/version_key), an explicit `released_at` operator action, tests for both.
H6 PUBLIC erasure (FCA kill switch) cannot reach firm caches and messages. ADR-002 D13a: roles write own tenant only, `fa_etl_public` only PUBLIC. Cached answers and conversation messages quoting COBS text live in firm tenants. R4's "purge cache rows by source_document_ids" and `purge_source` (cl.13: "immediately delete all copies") need a cross-tenant erasure role that D13a forbids; the source_epoch key makes old cache rows unreachable but does not delete them (24 h TTL). BigQuery rows (9 d) and Kafka copies (8 d) cannot be deleted immediately if FCA content or ids flow through them; P-simplicity keeps FCA content off Kafka and out of BigQuery. Missing: a defined `fa_erase` cross-tenant role with its own leak-matrix cases, a statement on whether messages quoting FCA text are deleted or kept as user-owned derived data (cl.19), and "FCA path is Kafka-free, ids-only in BigQuery".
H7 Deadlock/ordering between publish and erasure (feasibility item 3). Indexer: advisory lock (tenant, doc) then bumps the tenant's `corpus_version` row (hot row, serialises all publishes per tenant). A multi-document erasure (scope=source/tenant) in ONE transaction that locks doc 1, bumps corpus_version, then needs doc 2 (held by an indexer waiting for the corpus_version row) is a cycle. Postgres detects it (about 1 s) and aborts one side, so it is not silent but erasure can lose repeatedly. No starvation from lock fairness (waiters queue), but a long erasure tx blocks all publishes of that tenant. Missing rule: one document per erasure transaction, advisory lock first, tenant row last, retry with jitter; use pg_advisory_xact_lock only (safe under Cloud SQL pooling); test with two concurrent erasures plus an ingest storm.
H8 Wrong as_of silently. The model never sets as_of; a deterministic parser does ("year found in the question"). "Under the 2023 rules" has no unique date; "03/04/2024" differs between US and EU advisors; `current_date` depends on the session TimeZone (design says UTC calendar days but does not set it). Clock-skew test (+/-2 h, DST) covers app clock only. Missing: echo the resolved as_of in the answer text and chip every time it came from the parser; reject ambiguous formats by asking; `SET TIME ZONE 'UTC'` in the same set_config call.
H9 Entitlement change mid-stream cannot recall streamed text; accepted exposure is one answer. The numeric gate releases sentences before `done`, so a revoked advisor can have received N sentences of a now-forbidden document; persisted message says `refused` while the client saw text. Also Langfuse trace and cache hit paths: a cache hit re-verifies, fine. Missing: say in the ADR what is persisted (the text actually delivered) and that conversation rows containing text from a later-erased doc are in erasure scope via `retrieval_chunk_ids`.
H10 Knock-on of M4. Removing the `llm_regions` exclusion filter leaves: (a) Voyage embedding and rerank also send private EU document text to a US vendor at ingest and query time, not only the Anthropic prompt; ADR-038 must name all three egress paths; (b) cell isolation no longer implies failure isolation (one Anthropic/Voyage outage hits every cell, and `kill EU cell => US unaffected` is true only for data plane); (c) prompts hold "redacted" text whose redaction recall is unmeasured (Presidio), so tenant-private text can leave the region; (d) provider retention is outside the SLA (M3 says so) but Batch is not ZDR-eligible (ev §2.5). Missing: a per-tenant `llm_egress_ack` flag that the cell checks (default deny, enabled in the demo tenants), so the promise "data at rest" is a configuration, not an implicit behaviour.
H11 Derived BigQuery objects. R5 treats BigQuery as one store with `DELETE ... WHERE subject_ref IN`. dbt gold tables, snapshots, materialised views or table copies built from event rows each carry their own time-travel/fail-safe windows and are not in the lineage list ("BigQuery events"). Missing: erasure step enumerates every table/view in the dataset (INFORMATION_SCHEMA) and the reconcile invariant covers all of them.
H12 Hidden demo-on-demand conflict. Controls need an always-on or scheduled Postgres: erasure within 24 h plus VACUUM, hourly reconcile on ingest days, daily ledger export, weekly canary and golden-200, T+9 to T+14 d erasure-verify. Overview §2.5 budgets about 40 h up per month. If Cloud SQL is stopped, an erasure request waits for the next demo, which breaks "24 h" unless Cloud SQL stays up or the SLA says "while the demo environment is running". Not addressed.

Edge cases resolved by the design (no hole found): duplicate doc in two firms (apart from H5), poison document (quarantine + DLQ + breaker), partial region outage (421, no fallback), model retirement (preflight, fallback Sonnet 4.6 at $3/$15 budgeted), PUBLIC doc cached (key includes source_epoch; hit-time verifier), ACL change in flight (abort ENTITLEMENT_CHANGED, bounded exposure).

The weekly golden-200 ($17) should be cut to fortnightly, or the ablation one-off spread over more months; P-reliability itself admits current spend is an ASSUMPTION.
- Keshav §1.2: Kong unchanged (router "Kong/ALB host rule" adds an ALB host-rule dependency that plan.md lists as an unpriced spike); multi-tenant fully built stays; docker compose including Kafka stays (two-cell compose adds 4-6 GB RAM ASSUMPTION); demo-on-demand conflicts with H12. §1.3 non-goals not violated, but "synthetic data only" for Langfuse/Confluent/BigQuery is only kept because real documents are public publisher text; K-R4-3 private documents flow through Kafka/Langfuse/Voyage, so ADR-013/018's "real firm data" trigger must be restated as "real public documents allowed, real client data still not".
- IMPLEMENTATION GATE: the design file edits nothing in FinAdvisor and defines no build step; no violation. Two ordering problems: (a) "Gate before E1: 5-minute same-email test" and E1 listed as "update" while the brief says E0-E3 are complete; if the test fails, finished E1 identity work is reopened, so the test must run before the plan is approved, not "before E1"; (b) "E3 done tickets stay (migration adds columns)" and E5/E6 updates rewrite completed schema, so the re-plan must show these as new tickets, not edits of closed issues. No epic is S/M-sized by itself: E7 is "large" and E11-E13 bundle about 13 tables/jobs plus 25 tests; ticket-writers must split.

## Strongest dissent per major decision (task 5)

- Versioning (R3/M1): P-simplicity: valid time on chunks plus system time only on version rows, no EXCLUDE, partial unique index `WHERE valid_to IS NULL`, one `reconcile_lineage` for replay/late/withdraw; it already covers H3 and H4 and has valid_from in the chunk key. P-reliability's bitemporal model gives `known_at` reproducibility only for `document_versions`; chunks are extended in place, so chunk-level system history is not kept either (the same limitation P-simplicity states openly). Counter: P-reliability's constraint on versions is cheap; steal reconcile_lineage and valid_from-in-key.
- Deletion (R5/M2/M3): P-simplicity: no Kafka on the delete path, FCA path never in Kafka/BigQuery, ledger with tenant_id, SLA "10 d" built from documented windows with a measured number later; P-learning: HMAC pseudonym with a deletable DEK row (unlinkable at once, 7 d backup residue). P-reliability's strongest point is the two-phase receipt and ledger replay after restore; its weakest is a 60 s tombstone cache and a ledger with no tenant column.
- Cells (R7/M4): P-simplicity: cells are a config seam and an offline move runbook, no `llm_regions` machinery; P-learning keeps a directory table. With M4 dropping the egress filter, the cell code shrinks to `home_cell` check, 421 and the move protocol; tenant move with copy/verify/cutover/erase adds a state machine nobody deploys. Counter: Keshav asked for designed and locally tested cells (K-R4-1).
- Multi-login (R7): the one-tenant-per-firm design depends on an untested behaviour (same email in two Identity Platform tenants). Simplicity dissent: per-firm email aliases in the demo, no firm switcher UI in v1. P-reliability acknowledges the fallback; run the 5-minute test before approval.
- Guardrails (R10): ADR-009 says "no LLM-based guardrails on the hot path"; Model Armor latency is NOT FOUND and its timeout is set "from measured p99", i.e. unknown until built. Dissent: scanning trusted public law at ingest yields false-positive quarantines (regulatory words "ignore", "must") and a 5% batch circuit that can pause the connector. The numeric gate has no published precedent for a plain regex (ev §E5); its false-reject rate is unknown, and sentence-level release adds TTFT (see numbers).
- Eval stats (R11): 200 items cannot separate most arms (the file concedes); Holm across 9 arms plus McNemar leaves A4/A3 lines inconsistent (above); n_eff at or below 100 contradicts K-R4-4 unless clusters are redefined; the evalstats preprint (N<100 bootstrap warning) is a [PREPRINT] hypothesis; "inconclusive = off" is a sound default.

## Hidden assumptions

1. Document_versions is not partitioned (else the PG16 exclusion fails). 2. ICC 0.3 and "document" = provision. 3. Every sink and indexer honours tombstones with an uncached check. 4. Cloud SQL is running when erasure and verification jobs are due. 5. BigQuery datasets all carry 48 h time travel. 6. Langfuse delete works and no trace is written after the erase. 7. The same email can belong to two Identity Platform tenants. 8. Anthropic and Voyage prices/limits stay as read; Voyage batch is outside TPM. 9. FCA and publisher legal questions resolve favourably (K-R4-2/3 accepted the risk). 10. Weekly cloud canary and golden run fit the 40 h/month uptime.

## Most dangerous problem

A 60-second cached tombstone check plus a ledger without a tenant column means the design's central claim "tombstone implies absence everywhere" can be broken by replay or Kafka lag, and every resurrected BigQuery row silently resets the 9-day window behind the M3 "<= 14 d" SLA.
