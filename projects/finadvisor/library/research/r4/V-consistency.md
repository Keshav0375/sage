## Findings from 04, 04.1, 04.2, 05, 05.1
- [F6] GRANT GAP (blocking, 04.2 s4.19 vs 05 s5.3 / 05.1 s5.13): s4.19 Postgres advisor-erasure step order deletes `messages`, `turn_events`, `feedback`, `escalations`, `conversations`, `eval_scores`, `advisors` and `ingest_rejects`. s5.3 gives `fa_worker` no grant at all on conversations/messages/turn_events/feedback/escalations/advisors, only SELECT/INSERT on `eval_scores` and `ingest_rejects`; `messages` is owned by `fa_maint` ("no row access"). s5.3 says "plus the lifecycle tables of s5.13", and s5.13 lists only the deletion family and `pseudonym_map`. Fix: add DELETE grants + own-tenant policies for those tables to the `erasure-worker` (preferably a separate login role `fa_erasure`, since fa_worker also runs consumers), and state how `messages` (owned by fa_maint) is deleted from (partition-level DELETE through the parent needs a policy for the deleter; ownership does not matter for DELETE).
- [F7] GRANT GAP (blocking, 04.2 s4.20 / s4.17 vs 05.1 s5.13): `purge_source('fca_api')` and the PUBLIC `reconcile_lineage` call run as `fa_etl_public`. s4.19/s5.11 require the tombstone to be written first and the indexer to do an uncached ledger read. s5.13 grants `erasure_ledger` SELECT/INSERT, `erasure_steps`, `erasure_receipts` to `fa_worker` only, and `fa_worker` "writes limited to own non-PUBLIC tenant by policy". So nothing may write PUBLIC tombstones/steps/receipts, and the PUBLIC indexer path (s4.17 step 2) cannot read the ledger. A withdrawn then re-fetched FCA item is therefore unguarded. Fix: grant `fa_etl_public` SELECT/INSERT on the ledger/steps/receipts for the PUBLIC tenant only.
- [F8] CROSS-TENANT WRITE vs R4-D8 (05 s5.3 `fa_etl_public`, 05.1 s5.13 vs 04.2 s4.20): s4.20 says "There is no cross-tenant role (keeps ADR-002 D13a)"; s5.4 says INSERT/UPDATE/DELETE is "own tenant only" (D13a). But s5.3 and s5.13 give `fa_etl_public` "INSERT on `deletion_requests` of firm tenants ... for the purge_source fan-out". That is a cross-tenant write grant (narrowed, but real). R4-D8 says fan out "one erase job per firm tenant under that tenant's own role". Fix: either (a) have each firm's `erasure-worker` read the PUBLIC `source_epoch`/a PUBLIC `source_kill` row (SELECT on PUBLIC is allowed) and insert its own `deletion_requests` row, or (b) keep the grant but reword s4.20/ADR-029 to call it a single audited exception to D13a and add it to the leak matrix.
- [F9] Write guard coverage (04 s4.7 vs 05.1 s5.13): s4.7 lists the guarded sinks as silver, contextualizer, indexer, bq-sink. The `etl` job (`fa_etl`) writes the GCS bronze object and the `document_versions(ingesting)` row and publishes `docs.bronze.v1` BEFORE any guard; `fa_etl` has no SELECT on `erasure_ledger` (only fa_worker). After an erase-class withdrawal (publisher, FCA), a re-listing re-creates bronze bytes and a version row; only the end-of-window re-sweep removes them. Fix: add the connector fetch step to the guarded sinks and grant `fa_etl` and `fa_etl_public` SELECT on the ledger, or state the re-sweep as the only control for bronze.
- [F10] Lock/commit order text (04 s4.7 `indexer`, 04.1 Flow 2 vs 04.2 s4.17): s4.17 order is (5) cache purge, (6) processed_events, (7) `corpus_version` bump LAST. s4.7 and Flow 2 read "version active, `corpus_version` bump last, cache purge, `processed_events`". Fix: reorder s4.7 and Flow 2 text to match s4.17.
- [F11] Demo start order vs restore promise (04.1 Flow 5 vs 04.2 s4.19, 02 s2.7, R4-D9): Flow 5 brings the gateway and `chat-api` up (step "new Kong revision ... min instances up") before the erasure drain and before the "erasure-replay before traffic" restore check. s4.19 and s2.7 say replay runs "before traffic". Fix: move the gateway/min-instances step after the restore check and the first erasure drain (or keep the gateway at 0 / return 503 until `/readyz` after replay).
- [F12] Naming (04.1 Flow 2 step "document_versions row (ingesting), idempotent on (doc, version_key, content_sha256)", 04.2 s4.15 "(tenant, doc, version_key, content_sha256)" vs 05.1 s5.9 unique index `(tenant_id, doc_id, version_key, bronze_sha256)`): `document_versions` has `bronze_sha256`, not `content_sha256` (that name belongs to `source_observations`). Also `document_versions.content_hash` (ER, s5.9) is undefined next to `bronze_sha256`. Fix: use `bronze_sha256` in Flow 2 and s4.15; define or drop `content_hash`.
- [F13] ER vs table text (05 s5.1 deletion_requests `reason` list vs 05.1 s5.11): ER omits `source_kill`. Minor. Also ER `tenants.status "incl moving, moved"` vs the seven-state tenant move machine in 04.2 s4.24 (`freezing, copying, verifying, cutover, draining, source_erased`): state which column holds the move state (needs a `move_state` column or an enum on `tenants.status`).
- [F14] 04.2 s4.22 vs 02 s2.9: tombstone invariant frequency. s4.22 table runs it in the hourly `reconcile`; s2.9 says "hourly for 24 h after any erasure, then daily". Also s4.22 compares "published outbox rows vs `ingest_events`", but outbox also carries chat/audit/acl events, so the daily count/hash needs a per-topic scope (BigQuery tables are `chat_audit`, `chat_usage`, `eval_events`, `acl_changes`, `ingest_events`).
- [F15] 04 s4.13 does not list ESMA among Source publishers (s3 and s4.15 treat it as an optional source). Minor.
- [F16] Rerank model name vs R4-D17 arm (3) "rerank-3 vs rerank-2.5": arch default is `rerank-2.5-lite` everywhere (04 s4.5/s4.13, Flow 1) while arm (3) in 02 s2.10 compares `rerank-3` with `rerank-2.5` (not `-lite`). Fix: state in ADR-037 that arm 3's control is the shipped `rerank-2.5-lite` or change the default to `rerank-2.5`; check ADR-037 text. (Decision R4-D17 literally says rerank-2.5; the arch's default is -lite, so either the decision or the arch default must be amended.)
- [F17] EXCLUDE on `document_versions` (05.1 s5.9): the WHERE clause excludes only `ingesting`, `quarantined`, `erased`. A `withdrawn` or `revoked` version still holds an open `system_range` and its `valid_range`; a replacement/reinstated version over the same valid time then raises 23P01 unless the withdrawal closes `system_range`. Design risk, not a contradiction; add `withdrawn`, `revoked` to the exclusion list or require system-range closing in the same transaction (test in the reconcile_lineage permutations).
