## 1. Deletion windows
- CONFIRMED BigQuery time travel 2-7 days, default 7; fail-safe 7 days, not configurable, not directly queryable — https://docs.cloud.google.com/bigquery/docs/time-travel "from a minimum of two days to a maximum of seven days"; "The fail-safe period isn't configurable and can't be extended."; "You can't query data in fail-safe storage directly". Page shows no date (BC says 2026-10-27; not re-verifiable). So post-DELETE residue is 9 to 14 days.
- CONFIRMED Cloud SQL backups of deleted instances kept 4 days; no per-row purge statement — https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/backups "Cloud SQL retains the backups of deleted instances for four days." Page silent on rows. ADDITION: "After an instance is deleted, its automated backups are removed one per day on a rolling basis"; standard on-demand backups "stored indefinitely until manually deleted"; automated retention "1 day to 10 years". So the SLA ceiling is the longest backup retention you configure, not 4 days. The 4 days applies only after instance deletion, not to row-level erasure in a live instance (the claim as written in B is fine; a design that quotes "4 days" as the erasure SLA would be wrong).
- CONFIRMED GCS soft delete 7-90 days (default 7, 0 disables), not purgeable early — https://docs.cloud.google.com/storage/docs/soft-delete "you can customize the retention duration between 7 days and 90 days."; "the object or bucket can't be permanently deleted"; "To disable soft delete, you set the retention duration to 0." NB B's improvement line "set soft delete to 0 or the 7-day minimum" is right; "7-90, not purgeable early" is incomplete without "0 disables".
- CORRECTED Cloud Logging "no per-entry delete; erasure only by expiry, bucket delete, or not logging" — per-entry delete is indeed undocumented (https://docs.cloud.google.com/logging/docs/buckets silent), BUT a log-level delete exists: projects.logs.delete "Deletes all the log entries in a log for the global _Default Log Bucket." / "The log reappears if it receives new entries." (https://docs.cloud.google.com/logging/docs/reference/v2/rest/v2/projects.logs/delete). It works only for _Default, not custom buckets. So a fourth erasure path (delete the whole log in _Default; coarse, tenant-wide) exists. Decision impact: low-medium; "keep PII out of logs" stays the right rule.
- CONFIRMED Langfuse delete API async ~15 min; not plan-gated for session deletion — https://langfuse.com/docs/administration/data-deletion "Usually, trace data is deleted from our system within 15 minutes of the delete call." (typical, not a guarantee; no confirmation returned); rate-limited with no number; Hobby read window 30 d / Core 90 d for the session->trace lookup (verified).
- CONFIRMED Langfuse retention setting Pro/Enterprise only, min 3 days, nightly — https://langfuse.com/docs/administration/data-retention "we accept a number of days with a minimum of 3 days"; table: Hobby and Core "Not Available". Also: "does not delete audit logs or dataset items" (new: dataset items copied from traces survive retention and survive trace delete? not stated; treat as a possible PII residue).
- CONFIRMED KMS destroy default 30 days, configurable only at creation, min 24 h (import-only 0), max 120 days — https://docs.cloud.google.com/kms/docs/key-states (verbatim above).
- CONFIRMED KMS price per active key version, software: $0.000082192/hour = $0.06/month; versions in Enabled, Disabled and Scheduled-for-destruction states bill; destroyed free; $0.03 per 10,000 crypto ops — raw page via exa, https://cloud.google.com/kms/pricing, "Prices are effective March 17, 2025." B had this UNVERIFIED; now CONFIRMED. Per-subject key = $0.72/yr/key version (plus ~30 days of scheduled-destruction billing, trivial).
- CONFIRMED KMS quotas: no cap on keys/versions; from 2026-02-16 read 600 TPM, write 100 TPM per project, token-based, raisable; quota adjuster opt-in — https://docs.cloud.google.com/kms/quotas. NOTE: 100 write TPM is "tokens", not requests; per-subject key creation fan-out and DEK unwrap rates must be recomputed against the token table (not read here). Not "UNVERIFIED", but the per-operation token cost is unchecked.
- CONFIRMED Confluent max.compaction.lag.ms minimum 7 days on Basic/Standard/Enterprise (6 h Dedicated), editable — https://docs.confluent.io/cloud/current/topics/manage.html (Last updated Sep 25, 2026) "604,800,000 ms (seven days) for Basic, Standard, and Enterprise clusters". delete.retention.ms max 60,566,400,000 ms (=701 days) default 86,400,000: CONFIRMED.
- CONFIRMED Basic supports compacted topics (resolves B's UNVERIFIED gap) — https://docs.confluent.io/cloud/current/clusters/cluster-types.html "5 TB per partition for compacted topics"; 1,500 compactable partitions.
- CONFIRMED SR hard delete = soft then ?permanent=true (from B; not re-fetched this pass, see section 7).
- NOTE (hidden, see below): a 7-day minimum max.compaction.lag.ms means a key's old value is only ELIGIBLE for compaction after 7 days; compaction timing is not guaranteed, and tombstones live a further delete.retention.ms. Kafka erasure latency on Basic = >= 7 d + cleaner scheduling + tombstone retention (>= 1 d default).
- CONFIRMED (re-fetched) SR hard delete is soft then ?permanent=true; "A hard delete removes all metadata, including schema IDs."; soft-deleted IDs stay available and still count toward the schema limit — https://docs.confluent.io/cloud/current/sr/schemas-delete-cc.html

## 4. Paper numbers (all arXiv preprints unless noted; none peer reviewed as far as the arXiv record shows)
- CONFIRMED Anthropic contextual retrieval 35/49/67% — https://www.anthropic.com/news/contextual-retrieval (published Sep 19, 2024): "reduced the top-20-chunk retrieval failure rate by 35% (5.7% to 3.7%)"; Contextual Embeddings + Contextual BM25 "49% (5.7% to 2.9%)"; plus rerank "67% (5.7% to 1.9%)"; "Gemini Text 004"; "the Cohere reranker"; top-20; "$1.02 per million document tokens"; "smaller than 200,000 tokens (about 500 pages)". Resolves E's "NOT CONFIRMED". 
- CORRECTED how the 35/49/67% may be used: the 5.7% baseline is DENSE-ONLY embeddings. The 49% bundles contextual BM25 and the 67% bundles a reranker, so neither is "what CR adds to a hybrid+rerank pipeline" (ours). Only 35% is CR alone, on dense retrieval. Datasets are codebases, fiction, ArXiv, science papers (no legal/financial), one embedding model, first-party blog, 2024. $1.02/M assumed 2024 Claude pricing + caching; recompute with Haiku 5.5 batch.
- CONFIRMED FiscalQA Pro 2608.09393 (v1, 2026-08-10, Cymbler, Guez, Fabre) numbers — abstract and Table 1 text: parametric 3.0%, static current-version RAG 2.7% [CI 1.3, 4.8], multi-version retriever C_prod 98.3% [95.9, 99.6], oracle-article 99.1% [98.4, 99.9]; "gold version in the top-5 for 99% of questions (vs. 0% for B)". 
- CORRECTED interpretation of 2.7% vs 98.3%: the 209 questions are "all-model-hard", selected because no model answered closed-book and "the currently in-force text lacks the gold value for all but one of the scored questions"; the C_prod retriever is "conditioning retrieval on the query date" and is the authors' own (fine-tuned encoder weights not released). So 2.7% is a floor by construction (version-drift-only questions), 98.3% needs an explicit as-of date in the query. Not a prediction of FinAdvisor's gap. Direction (hard validity filter beats current-version-only) is solid; magnitude is not transferable. Single preprint, French tax, 33 articles.
- CONFIRMED 2603.23533v4 (Mangla, 2026-03-08) — abstract: "7B enrichment beats a free section-path prefix under a hybrid retriever by +5.5 recall points on Qasper"; FreshStack +2.7 "does not survive Holm adjustment"; "equivalent to CR, which sends 5.8-8.7 times the input tokens"; under qwen3-embedding + reranker "within the equivalence margins"; "free prefix under either strong retriever beats hybrid enrichment by +3.4 to +6.3 points"; "best 120B-indexed configuration leads the best free one by +2.5 on Qasper". Also confirmed in-text: "Versions 1 and 2 ... reported an evaluation ... that we found invalid". PREPRINT, single author, off-domain (science papers, tech docs), 7B/120B open models, English. G's note that it is not "contextual retrieval vs section prefix" is right: CR arm is compared to enrichment, and the free-prefix comparison is against enrichment, not CR directly.
- CONFIRMED VersionRAG 2510.08109 (2025-10-09) — abstract: "VersionQA benchmark-100 manually curated questions across 34 versioned technical documents-VersionRAG achieves 90% accuracy, outperforming naive RAG (58%) and GraphRAG (64%)"; "60% accuracy on implicit change detection where baselines fail (0-10%)"; "97% fewer tokens during indexing than GraphRAG". PREPRINT; the authors built the benchmark; 100 questions; software docs.
- CONFIRMED FinGround 2604.23588 (2026-04-26) — text: "FinGround achieves the lowest hallucination rate across all benchmarks (4.1% avg.), a 78% relative reduction from GPT-4o + CoT (p<0.01)"; abstract: with identical retrieval "reduces hallucination rates by 68% over the strongest baseline"; 8B distilled detector "91.4% F1 at 18x lower per-claim latency" and "$0.003/query"; ablations 4.9% to 11.7% (FinanceBench no taxonomy) and 3.8% to 10.6% (TAT-QA no table retrieval). PREPRINT; FinHalu is the authors' dataset; labels come from GPT-4o (expert kappa 0.87 vs GPT-4o on 200 examples; distilled detector 90.8% F1 vs humans); regeneration introduces errors in 4.1% of cases (per-answer 14.3% for >=3 claims); detector transfers 3-4 F1 points worse to other generators (Claude-3.5-Sonnet 87.6). HalRate is claim-level and LLM-judged; do not read 4.1% as an answer-level error rate.
- CORRECTED Spotlighting 2403.14720 — abstract "from greater than 50% to below 2%" is true but: tested on text-davinci-003, GPT-3.5-Turbo and GPT-4 (June 2023 versions); plain delimiting only "can reduce the ASR by half"; the large effect is datamarking (GPT-3.5 from ~50% to below 3%, Text-003 40% to 0%) and encoding (0.0% summarization, 1.8% Q&A on GPT-3.5); the authors "do not recommend" delimiting and recommend "at least datamarking"; encoding "should only be used with appropriate LLMs". No Claude or 2026 model tested, static attacks. E's line "delimiting / datamarking / encoding ... >50% to <2%" blurs this.
- CONFIRMED InjecGuard 2410.22770 (abstract only; full text not downloaded): NotInject 339 benign samples; guard models "accuracy dropping close to random guessing levels (60%)"; InjecGuard "surpassing the existing best model by 30.8%". ## 6. Hidden assumptions (not in the evidence files)
1. The "erased within N days" statement is a max over systems and each window starts only when the previous layer finishes: BQ 9 to 14 days after DELETE; GCS soft delete 7 d (0 = off); Kafka Basic >= 7 d (max.compaction.lag floor, eligibility not guarantee) + cleaner scheduling + delete.retention.ms (default 1 d) ; Cloud SQL = longest of automated retention (1 d to 10 y, your setting), PITR logs (retention days NOT found) and any manual backups ("indefinitely until manually deleted"); Langfuse ~15 min typical. Nobody has measured an end-to-end erasure, and only per-system latencies are documented.
2. Crypto-shredding with Cloud KMS assumes the data key is not cached or re-wrapped elsewhere. Destroy has a 24 h minimum (30 d default, set only at key creation, so the shred window must be chosen at creation or every key inherits 30 d); versions in Scheduled-for-destruction still bill; BigQuery AEAD shredding is an inference no doc describes; Cloud SQL docs only say enhanced backups encrypted with a destroyed key version become unrestorable. KMS quota 100 write TPM is "tokens" after 2026-02-16; per-subject key creation bursts may hit it (raisable, adjuster is opt-in).
3. Cloud Logging log-level delete exists only for _Default; custom buckets have none. Entries can reappear.
4. Langfuse: dataset items and audit logs survive both retention and "project data retention does not delete audit logs or dataset items"; whether per-trace delete also removes dataset items copied from traces is NOT stated. Session-to-trace lookup after 30 days fails on Hobby, 90 on Core. Store trace IDs at write time.
5. Temporal FKs in PG18 do not cascade (RESTRICT/CASCADE/SET NULL/SET DEFAULT unsupported). Tenant delete needs an ordered explicit delete; btree_gist required for uuid/int keys (extension 1.8 on PG18).
6. Temporal retrieval gain assumes the question carries or implies an as-of date. FiscalQA's retriever "condition[s] retrieval on the query date". Casual FinAdvisor questions may not state one; the default date policy (today) decides how often the filter does anything.
7. Contextual retrieval: baseline in Anthropic's numbers is dense-only; our pipeline is hybrid FTS+vector+rerank with a free section prefix; the independent paper is off-domain and 7B. Neither supports the flag default either way; the arms (free prefix, Voyage voyage-context-4, LLM CR) must be measured on the project's eval set. LLM CR cost: 5.8-8.7x tokens (Mangla), Anthropic $1.02/M doc tokens (2024).
8. Spotlighting datamarking interleaves a marker token between every word. That alters quoted text and may break the "every number appears in a cited span" regex gate and DE/FR "1.234,56" formats. Unvetted interaction. Tested only on 2023 GPT models.
9. Model-version churn: Haiku 4.5 retirement date has passed its "not sooner than" and is still Active; 60 days is a floor, not a schedule. Partner platforms differ. API 2026-10-21 removed temperature/top_p/top_k (400 error): any pinned-parameter code breaks on the new API version.
10. Confluent Basic is a shared, non-editable cluster config; topic-level only; Basic has no RBAC for Kafka resources, 99.5% SLA. Retention max.ms on Basic not found. Cost rates for Basic are from a summarized pricing page, not raw.
11. All four evidence files rely on WebFetch's summarizer. This pass used raw text for KMS pricing, Voyage docs, Anthropic docs, PyPI JSON and arXiv full text; Google docs, Langfuse, Confluent, PostgreSQL and Notion quotes are again "as relayed" by the summarizer (two independent fetches agreeing, not byte-verified).
12. Single-source preprints carrying decisions: FiscalQA Pro, 2603.23533 (v1-2 retracted by author), FinGround, evalstats, VersionRAG, 2604.01432, InjecGuard (2024, maybe published at a venue; not checked). Treat each as a hypothesis for an ablation, not as an effect size.
