## Summary
Add the `pseudonym_map` table and a `pseudonym_id` column on `conversations` and `messages`, with RLS and grants, so deleting the mapping row unlinks surviving rows.

## Description
E1 owns `pseudonym_map` (plan E1, Validation 2026-11-07; it is created with `advisors`). Arch (deep-dive/05-1 section 5.12): "`pseudonym_map` | `(tenant_id, advisor_id)` | `pseudonym_id uuid NOT NULL UNIQUE`, random (not derived from `idp_uid` or email). Outbox events, BigQuery rows, Kafka payloads, Langfuse metadata and logs carry `pseudonym_id` only. Erasing an advisor deletes the mapping row at once, so surviving rows in slow stores become unlinkable immediately while physical deletion runs inside the windows. Unlinking is not claimed as erasure" (ADR-029).

Add an Alembic revision as `fa_owner`:
- `pseudonym_map (tenant_id uuid NOT NULL, advisor_id uuid NOT NULL, pseudonym_id uuid NOT NULL UNIQUE DEFAULT gen_random_uuid(), PRIMARY KEY (tenant_id, advisor_id), FOREIGN KEY (tenant_id, advisor_id) REFERENCES advisors (tenant_id, id))`; `ENABLE` and `FORCE ROW LEVEL SECURITY` at creation. The value is generated by `gen_random_uuid()` only; no column or function derives it from `idp_uid` or email.
- Policies and grants (section 5.13): INSERT `TO fa_app` when `app.role = 'tenant_admin'` and `tenant_id = app.tenant_id` (the row is inserted together with the advisor row); SELECT for `fa_app` and `fa_worker` on own tenant; DELETE `TO fa_worker` on its own non-PUBLIC tenant; no UPDATE for anyone; policies call `current_setting('app.x')` without `missing_ok` (fail closed).
- A function-free helper in the seed path: `migrate --seed-advisors` (E1-T11) inserts one mapping row per seeded advisor (E1-T11 is updated for this).

Out of scope: writing `pseudonym_id` into outbox events, Kafka, BigQuery or logs (E5, E6, E9), the advisor erasure step that deletes the row (E12-T10), adding `pseudonym_id` columns to `conversations` or `messages` (the arch specifies only this table; see the report question).

Confirmed by the orchestrator (R4-D6 subject rows): `conversations` and `messages` (created by E1-T6; `messages` is monthly-partitioned, so the column is added on the parent) also get `pseudonym_id uuid NOT NULL`, set at insert from the advisor's `pseudonym_map` row (the same value, never derived from `idp_uid` or email), with no foreign key to `pseudonym_map` so deleting the mapping row leaves the surviving rows intact but unlinkable. Existing RLS on both tables is unchanged. The `chat-api` write path that fills the column is E4; this ticket adds the columns, a CHECK-free NOT NULL and a DB test helper `fa_pseudonym_for(tenant_id, advisor_id)` is NOT added (the app reads the map).

## Acceptance criteria
- [ ] Given `alembic upgrade head`, when `tests/db/test_schema_pseudonym_map.py` runs, then `pseudonym_map` exists with `relrowsecurity` and `relforcerowsecurity` true, `pseudonym_id` is UNIQUE NOT NULL, and its default is `gen_random_uuid()`.
- [ ] Given two advisors inserted through the seed path, then their `pseudonym_id` values differ, are valid UUIDv4, and neither equals the advisor `id` nor `md5`/`sha256` of the `idp_uid` or email (`test_pseudonym_not_derived`).
- [ ] Given the mapping row of advisor X is deleted as `fa_worker` of the same tenant, then `SELECT` of that `pseudonym_id` returns no row and the `advisors` row is untouched; given `fa_worker` of tenant B deletes it, rowcount is 0 (`tests/db/test_pseudonym_map_rls.py::test_delete_unlinks_and_is_tenant_scoped`).
- [ ] Given `fa_app` with `app.role = 'advisor'` inserts a mapping row, then it raises a row-level-security violation; with `tenant_admin` it succeeds for its own tenant and fails for tenant B (`test_insert_only_for_tenant_admin`).
- [ ] Given any role attempts UPDATE of `pseudonym_id`, then it raises permission denied (`test_no_update`).
- [ ] Given the migration, then `conversations.pseudonym_id` and `messages.pseudonym_id` exist as `uuid NOT NULL` with no FK to `pseudonym_map` (`tests/db/test_schema_pseudonym_map.py::test_subject_rows_carry_pseudonym_id`).
- [ ] Given a conversation and message inserted with an advisor's `pseudonym_id`, when that advisor's `pseudonym_map` row is deleted as `fa_worker`, then both rows remain and no query can resolve their `pseudonym_id` back to `advisors` (join returns zero rows) (`test_unlink_after_map_delete`).
