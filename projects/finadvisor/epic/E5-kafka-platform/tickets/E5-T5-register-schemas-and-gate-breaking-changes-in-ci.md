## Summary
Register every topic's JSON Schema in Schema Registry and fail CI on a backward-incompatible change, including the docs.* and chunks.* contracts.

## Description
Add `scripts/register_schemas` that registers, for each topic, a JSON Schema generated by E5-T4 under subject `<topic>-value` with the registry's default compatibility, which is BACKWARD (6.4: 'registry default compatibility'; do not override it). A topic carrying several event types uses a oneOf schema over its envelopes. Round 4 (ADR-013 amended, ADR-034): the `docs.*` and `chunks.*` event schemas are data contracts, BACKWARD, checked in CI, so the compatibility check names them explicitly in its report. Add a CI job (compose Schema Registry) that (1) registers the current schemas into an empty registry, (2) runs the registry compatibility check API for the checked-in baseline vs. the working tree, and fails when incompatible. Check in the baseline snapshot under backend/schemas/. Settings: SCHEMA_REGISTRY_URL/_API_KEY/_API_SECRET. `dlq.v1-value` is registered too (11 subjects including dlq.v1). Out of scope: Confluent Cloud registration (E5-T13); a `source_observations` event contract is not in the 6.4 catalogue, so none is registered here (see questions).

## Acceptance criteria
- [ ] Given an empty registry, when the script runs, then `GET /subjects` lists 11 subjects `<topic>-value` (integration test).
- [ ] Given a model change that removes a required field from `DocBronzeLanded` (docs.bronze.v1), when the CI compatibility step runs, then it exits non-zero and names the subject `docs.bronze.v1-value` (test with a breaking fixture).
- [ ] Given a change that adds a required field to a `chunks.*` payload, when the step runs, then it exits non-zero; given an optional field added, it exits zero.
- [ ] Given the registry compatibility level of every subject, when read, then it equals BACKWARD (test).
- [ ] Given the script is run twice, when subjects are listed, then no new versions are created (idempotent).
