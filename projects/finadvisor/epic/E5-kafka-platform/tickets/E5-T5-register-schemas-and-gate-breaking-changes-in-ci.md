## Summary
Register every topic's JSON Schema in Schema Registry and fail CI on a breaking change.

## Description
Add `scripts/register_schemas` that registers, for each topic, a JSON Schema generated by E5-T4 under subject `<topic>-value` with the registry's default compatibility (deep-dive/06-interfaces-and-contracts.md#6.4; do not override it). A topic carrying several event types uses a oneOf schema over its event types' envelopes. Add a CI job (compose Schema Registry service) that (1) registers the current schemas into an empty registry, (2) runs the registry compatibility check API for the checked-in baseline vs. the working tree, and fails when incompatible. Check in the baseline snapshot of schemas under backend/schemas/. Settings use SCHEMA_REGISTRY_URL/_API_KEY/_API_SECRET. Out of scope: Confluent Cloud registration (done by the same script with cloud env in E5-T13). Per R56: one oneOf schema per topic under `<topic>-value`, and `dlq.v1-value` is registered as well (so subject count = 11 including dlq.v1).

## Acceptance criteria
- [ ] Given an empty registry, when the script runs, then `GET /subjects` lists 11 subjects `<topic>-value`, one per catalogue topic (integration test).
- [ ] Given a model change that removes a required field from a payload, when the CI compatibility step runs, then it exits non-zero and names the subject (test with a deliberately breaking fixture).
- [ ] Given a backward-compatible change (optional field added), when the step runs, then it exits zero.
- [ ] Given the script is run twice, when subjects are listed, then no new versions are created (idempotent).
