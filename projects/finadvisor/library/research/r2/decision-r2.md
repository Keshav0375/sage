# Round-2 decision brief (orchestrator, 2026-11-01)

Inputs: requirements.md, evidence-r2.md, three solution-architect proposals (simplicity, scale, cost).
Name: "FinAdvisor v2 — pooled multi-tenant modular monolith, event-driven ingest, demo-on-demand".

## Where all three proposals agree (adopted as is)
1. Pool tenancy in one Postgres (Cloud SQL PG16, pgvector 0.8.5): tenant_id NOT NULL on every table; ENABLE+FORCE RLS on all tenant tables; app connects as a non-owner, non-superuser, NOBYPASSRLS login role (no SET ROLE); per-transaction `set_config('app.*', $n, true)` with bind params; current_setting without missing_ok (fail closed); short transactions never held across the LLM loop; composite FKs (tenant_id, …) because FK checks bypass RLS; migrations as a separate owner role in a Cloud Run job; startup/readiness asserts role flags, FORCE RLS on every table, pgvector ≥ 0.8.
2. A reserved PUBLIC tenant holds the public corpus (EDGAR); policy allows own tenant OR public.
3. Single retrieval enforcement point (`RetrievalService(principal)`); tools never take tenant/tier/jurisdiction arguments; import-linter + test forbid other modules touching content tables. Entitlements (tier, jurisdictions, licenses, role) come from `advisors` in the DB with a 60 s cache; the token only identifies (sub, tenant).
4. Drop LiteLLM (Kong: see D12, Keshav's decision). Thin in-process `LLMClient` over the Anthropic SDK: streaming, explicit timeouts, retries with jitter, circuit breaker, same-provider fallback only (claude-sonnet-5-5 → claude-sonnet-4-6). No cross-provider fallback (changes regulated answers). Model ids only from config; no temperature/top_p/top_k; CI + readiness fail on a retired or soon-retiring model.
5. Models: answer claude-sonnet-5-5; judge, contextual headers, rule extraction, citation spot-checks claude-haiku-5-5 (judge ≠ answer model); Batch API for offline/bulk. Prompt caching on system prompt + tools; tenant/user/date text after the breakpoint.
6. Retrieve-first orchestration: retrieval runs in code before the first LLM call, injected as a JSON-encoded tool_result; one streaming call with tools (factsheet, suitability, escalate, follow-up search), max 3 iterations, max_tokens bound.
7. Retrieval: Voyage voyage-4 embeddings with input_type=query/document; halfvec(1024); HNSW (m16, ef_c 64) + `SET LOCAL hnsw.iterative_scan=relaxed_order`, max_scan_tuples 20000, ef_search ~80-100; tsvector+GIN FTS leg (websearch_to_tsquery) for rule IDs/tickers; RRF k=60 in one SQL statement with RLS on both legs; Voyage rerank-2 top 20-30 → 6 with timeout and fail-open to RRF order, kept or gated by eval ablation; CRAG-style confidence gate (no web fallback) → "no firm documentation" + escalate offer without an LLM call; parent expansion; staleness computed server-side from today's date.
8. Chunking: structure-aware 256-512-token children + ~1k-token parents; title > section heading prefix.
9. Guardrails (OWASP LLM 2025): Cloud Armor edge limits; input cap; Presidio in-process pseudonymization before embed/LLM/traces/logs; Model Armor input screen in parallel with embed (500 ms timeout, fail closed); untrusted content only in JSON tool_result; least-privilege tools, escalate uses server-side licenses and persists; client receives tool name+status only, never tool payloads; errors carry codes not exception text; sentence-buffered output PII redaction; deterministic citation verifier (every [n] ∈ retrieved chunk ids, quote overlap; EvidenT-style), server-emitted citation events with redacted excerpts; React renders sanitized markdown only; no LLM-based rails on the hot path.
10. Auth: Google Identity Platform; API verifies ID tokens (sig, aud, iss, exp) via JWKS. Network: Cloud Run ingress internal-and-cloud-load-balancing, no allUsers; per-service SAs + run.invoker + ID tokens; Cloud SQL private (PSC); Direct VPC egress with startup probe; Secret Manager; WIF for GitHub; no secret defaults in code (fail to boot).
11. Kafka on Confluent Cloud Basic in the cloud (GCP Managed Kafka rejected: ~$189-248/mo); apache/kafka:4.4.0 KRaft locally; confluent-kafka 2.16.1; idempotent producers; at-least-once consumers with idempotent sinks (`processed_events`); DLQ topic; key by tenant; chat never depends on Kafka.
12. Ingest is idempotent: bronze GCS by sha256; chunk unique (tenant_id, chunk_hash, embed_model); re-embed only changed chunks; ACL change = metadata UPDATE (Notion). documents.raw_content dropped; raw bytes only in bronze. suitability_rules extracted (Haiku structured output) and validated (G-07).
13. Evals: L0 deterministic (RLS leak matrix incl. pooled-connection reuse, fail-closed, citation verifier, PII, model-retirement check) every PR on real pgvector + Kafka service containers; L1 retrieval recall@k/MRR/nDCG with dense/FTS/hybrid/rerank ablation; L2 Ragas collections (faithfulness, context precision/recall, noise sensitivity) with Haiku judge calibrated on ~30 human labels (Cohen's κ), CI lower bound reported; L3 cross-tenant/tier/jurisdiction refusal + promptfoo red team; L4 online sampled judge + thumbs. Golden set 50 → ~300, tenant-parameterised. Gate: citation ≥ 0.95, faithfulness ≥ 0.90, leaks = 0, recall regression ≤ 2 pts. PR = ~60-question path-filtered subset; full set weekly and before demos.
14. Observability: Langfuse Cloud Hobby (SDK v3+ @observe/context managers, wrapped, scrubbed input only); OpenTelemetry → Cloud Trace (free to 2.5M spans), structured redacted logs, log-based metrics (TTFT, gate refusals, guard blocks, consumer lag), /healthz + /readyz (DB roles, Kafka, model availability), one availability SLO + burn-rate alert, budget alerts.
15. Compute: one Python image, entrypoints api | worker | jobs. Cloud Run service chat-api (SSE, explicit concurrency, timeout 3600 with Last-Event-ID resume + Idempotency-Key), Cloud Run worker pool for consumers, Cloud Run jobs (migrate, etl, dbt, eval, redteam, demo-ttl). Vite React+TS SPA. Local dev = docker compose.
16. Demo-on-demand: Terraform owns everything; `make demo-up/demo-down` flips Cloud SQL activation policy, API min instances, worker pool count, Scheduler pause; hourly auto-down TTL job as a safety net; prewarm on up.
17. CI/CD: GitHub Actions + WIF, lockfile installs, ruff/mypy/pytest, eslint/tsc/vitest, trivy/gitleaks/pip-audit, eval gate on the runner, image by digest to Artifact Registry, terraform fmt/validate/plan on PR, migrate job before traffic, tagged no-traffic deploy + smoke + shift.

## Where they differ — decisions
D1 Retrieval as a separate service (scale) vs in-process module (simplicity, cost).
  → In-process `RetrievalService` module in chat-api, plus a dedicated DB login role `fa_retrieval` used only by that module's pool (chat-api's general pool `fa_chat` has no grant on content tables). Gets the scale proposal's grant separation without a network hop (+latency, +service). Extraction to its own Cloud Run service is a documented trigger (separate scaling needed, or a second consumer of retrieval).
  Dissent (scale): a network boundary is stronger isolation than a module boundary.

D2 Partitioning `chunks` from day one (scale) vs at a trigger (simplicity, cost).
  → HASH(tenant_id) partitions (8) from day one, HNSW + GIN per partition. Cheap at demo size, expensive to retrofit (needs a replay), and a stated learning goal (databases at scale). Trigger to grow partitions or silo a tenant via `tenants.shard_id` seam: one tenant > 250k chunks, total > 2M chunks, or ANN p95 > 100 ms.
  Dissent (simplicity): adds 8 indexes and planner complexity for 3 tenants.

D3 ETL tooling: SQL views only (simplicity) vs Dagster + dbt (+BigQuery) (cost, scale).
  → Dagster OSS assets (partitioned tenant × date, run_key dedupe) executed as Cloud Run jobs from Cloud Scheduler, `dagster dev` locally, no cloud daemon until > 10 tenants or a sensor is needed; dbt Core for gold models on Postgres; BigQuery marts for audit/usage/eval analytics (partitioned by day, clustered by tenant_id, max bytes billed), fed by a Kafka sink worker with event-id dedupe. Docling for parsing (HTML + PDF filings). Keshav's explicit goal is to learn ETL/data engineering; all three tools are free at this size.
  Dissent (simplicity): a second platform to run and learn; SQL views would suffice for the product.

D4 Outbox for chat audit/usage/eval events (cost, scale) vs fire-and-forget (simplicity).
  → Transactional outbox table + relay loop in the worker (no Debezium). Audit in a compliance product must not be lost when Kafka is down. Debezium outbox connector is a later, optional learning epic.

D5 Schema Registry (none in all three).
  → JSON Schema in Confluent Schema Registry (Essentials, free in cloud; cp-schema-registry container locally) with versioned topics `*.v1`; Pydantic models generate the schemas. Kafka learning goal; small cost.
  Dissent (all three): extra component; Pydantic envelopes alone work.

D6 Auth mode: single pool (simplicity, cost) vs Identity Platform multi-tenancy (scale).
  → Identity Platform multi-tenancy (one IdP tenant per firm), billing enabled (needed for > 2 tenants; email/password tier free to 50k MAU). Gives per-firm sign-in configuration and an SSO path. Token gives sub + tenant; entitlements still from DB.

D7 Edge: Firebase Hosting + public API with JWT (cost) vs ALB + Cloud Armor (simplicity, scale).
  → External ALB + Cloud Armor, same origin: /* → GCS bucket (SPA, CDN), /v1/* → chat-api (ingress internal+LB). Persistent (~$18-25/mo) because cert provisioning is slow. Closes G-02 properly.

D8 Cloud SQL size: g1-small (simplicity) vs Enterprise 2 vCPU/8 GiB stopped by default (cost).
  → Enterprise 2 vCPU / 8 GiB, zonal, stopped by default (activation policy), HA as a Terraform flag for load tests.

D9 Answer cache: defer (simplicity) vs exact-match keyed cache (cost, scale).
  → Exact-match answer cache in a Postgres UNLOGGED table, key = hash(tenant, tier, jurisdiction set, corpus_version, prompt_version, model, normalized redacted question), single-turn only, 24 h TTL. No semantic cache (cross-user leak risk in a regulated product).

D10 Contextual retrieval at ingest: defer (simplicity) vs on (cost, scale).
  → On, generated with Haiku 5.5 via Batch API, behind a flag; the L1 ablation decides whether it stays. Must pass PII scrub and tier rules.

D11 Conversation state: Postgres `conversations`/`messages` (messages range-partitioned by month), last 6 turns ≤ 3k tokens, follow-up condensation with Haiku only when history exists.

D12 Kong (Keshav, 2026-11-01: "include kong for rate limiting and proxy plugins as well we need it") — binding.
  Facts (Kong docs check, 2026-11-01): Kong OSS ends at 3.9.x (latest 3.9.4, 2026-10-12); 3.10+ has no free mode (kong/kong-gateway needs a license) → pin `kong:3.9.4`, `_format_version: "3.0"`, DB-less. OSS has rate-limiting (limit_by consumer|credential|ip|service|header|path; policies local|redis in DB-less, `cluster` rejected), request-size-limiting, cors, correlation-id, ip-restriction, bot-detection, request/response-transformer, pre-function, prometheus, opentelemetry, http-log, proxy-cache, ai-proxy, ai-prompt-guard. Enterprise-only: openid-connect (JWKS), rate-limiting-advanced, ai-rate-limiting-advanced, ai-proxy-advanced, ai-semantic-cache, ai-sanitizer. OSS jwt plugin uses static per-consumer keys (no JWKS) → cannot verify rotating Google ID tokens. OSS ai-proxy 3.9 has no native Anthropic Messages format (llm_format anthropic is 3.10+).
  Decision:
  - Placement: edge API gateway. External ALB + Cloud Armor → Kong (Cloud Run service `fa-gateway`, ingress internal-and-cloud-load-balancing, admin API off, status listener for health) → chat-api (Cloud Run, ingress internal, run.invoker granted only to the Kong service account). SPA stays on the GCS backend bucket behind the same ALB.
  - Kong → chat-api IAM: a Kong `pre-function` fetches a Google ID token from the metadata server (audience = chat-api URL, cached until near expiry) and sets `X-Serverless-Authorization`, leaving the user's `Authorization: Bearer <Identity Platform token>` intact for FastAPI. VERIFY in a spike; fallback = ingress-internal only + app JWT (no IAM on that hop), recorded as an ADR if used.
  - Token verification stays in FastAPI (JWKS). Kong does not trust or set identity headers; a request-transformer strips any client X-User-Id / X-Tenant-Id / X-Serverless-Authorization.
  - Rate limits in Kong (OSS only): per client IP (anti-abuse) AND per bearer token (`limit_by: header`, `header_name: Authorization` = per signed-in session; a forged token gets rejected by FastAPI and is still bounded by the per-IP limit); stricter limit on POST /v1/chat; request-size-limiting; 429 with Retry-After. Policy `redis` against Valkey (local container in dev; Memorystore Valkey shared-core-nano ~$23/mo in cloud, created by `demo-up` and deleted by `demo-down`), sync_rate 0 on the chat route. Per-tenant token budgets and per-tenant concurrency stay in FastAPI (Kong OSS cannot key on a verified tenant claim). Cloud Armor keeps DDoS/WAF/geo rules.
  - Other Kong plugins: cors (SPA origin allow-list), correlation-id (X-Request-Id → propagated to FastAPI logs/traces), opentelemetry (traceparent to Cloud Trace), prometheus (scraped locally; Cloud Monitoring via OTel), http-log → an internal FastAPI `/internal/audit/gateway` route (fixes G-48) or file-log to stdout, bot-detection, ip-restriction on /internal/*.
  - SSE through Kong: chat route `response_buffering: false`, `request_buffering: false`, service read_timeout 3,600,000 ms (Cloud Run max 60 min). VERIFY in the spike that tokens stream without buffering through ALB → Kong → chat-api.
  - LLM egress ("proxy plugins"): spike — Kong ai-proxy 3.9 `route_type: preserve` (or a plain proxy service) to api.anthropic.com with streaming + tool use; if the spike passes, LLMClient calls Anthropic through an internal Kong route that adds the API key (request-transformer from env), a global LLM rate limit, and token statistics (`log_statistics`); if it fails, LLMClient calls Anthropic directly and the egress route is dropped (ADR). Native Messages format is required (no OpenAI-format translation: it changes tool-call fidelity).
  - Local: kong:3.9.4 + valkey containers in docker compose; kong.yml in git, validated in CI (`kong config parse`) and tested with deck/curl smoke tests.
  - Cost: fa-gateway Cloud Run min 0 (demo), max 2; Valkey ~$0.03/h only while the demo is up.
  - Not used: Konnect (paid), Enterprise image, openid-connect, ai-* Enterprise plugins.
  Dissent (cost, simplicity, scale proposals): Kong OSS duplicates Cloud Armor + FastAPI limits, cannot see the verified tenant, and adds a hop and a Cloud Run service; kept because Keshav requires it.

D13 Corrections after the skeptic (2026-11-01; tested pgvector 0.8.7 / PG16.15) — all adopted.
  a. RLS write split (most dangerous finding). SELECT policy: own tenant OR PUBLIC. INSERT/UPDATE/DELETE policies: own tenant only (WITH CHECK tenant_id = app.tenant). No app role has write grants on PUBLIC rows; only the `fa_etl_public` role (public-ingest job) writes PUBLIC. The L0 leak matrix tests writes as well as reads (cross-tenant insert, update into PUBLIC, FK existence probes).
  b. Partitioning: LIST partitions by tenant_id (one per tenant, one for PUBLIC, plus DEFAULT), not HASH(8) — 4 keys in 8 hash buckets collide ~59%. Tenant onboarding creates its partition + indexes (migration job). Runtime pruning with the RLS current_setting policy is CONFIRMED by test ("Subplans Removed: 6 of 8"). PUBLIC (EDGAR, largest) can be sub-partitioned by source later (trigger: > 250k chunks).
  c. D1 revised: one DB login role per process (`fa_app` for chat-api, `fa_worker` for workers, `fa_etl` / `fa_etl_public` for jobs, `fa_dbt` for dbt, `fa_owner` for migrations only). Content-table access is restricted to the RetrievalService module by import-linter + tests; RLS is the backstop. Two pools in one process are dropped (double connections, two snapshots, nominal boundary). Extraction of retrieval into its own service with its own role stays a trigger.
  d. Entitlements: cached ≤ 60 s per process AND invalidated on `acl.changes.v1` events; the revocation lag is documented (≤ 60 s worst case).
  e. Rerank: Voyage rerank-2 is an older model → rerank-2.5-lite (or rerank-2.5), $0.05/M. Tier-1 rerank limit is 2M TPM → at 10-15 candidates × ≤ 400 tokens ≈ 6k tokens/query ≈ 5 QPS on Tier 1; request a tier upgrade before load tests; a 429 must be counted and alerted (no silent fallback to RRF). The ablation decides rerank on recall AND latency. Latency targets revised (estimates, to be measured): TTFT p50 < 2.0 s, p95 < 3.5 s with rerank; retrieval first stage (embed + SQL) p95 < 300 ms; rerank p95 < 700 ms; full answer p95 < 8 s.
  f. Same-provider fallback claude-sonnet-4-6 costs 50% more ($3/$15), has a 1,024-token cache minimum and its own cache: budget it, and run the eval gate against the fallback model too (fallback is enabled only if it passes the gate). Sonnet 5.5 cache minimum 512 tokens; cache order tools → system → messages; changing tool definitions invalidates the cache (version tools with the prompt).
  g. Availability: demo mode has no SLA (zonal Cloud SQL, stopped by default; Confluent Basic 99.5%). The 99.5% SLO applies to the `prod` profile only (HA Cloud SQL flag, min instances ≥ 1); this is stated in overview §2 and §7.
  h. Demo-down order: stop Scheduler triggers (except the hourly demo-ttl job, which stays active) → drain the outbox and Kafka consumers to idle → scale worker pool to 0 → API/Kong min 0 → delete Valkey → stop Cloud SQL. Terraform uses lifecycle.ignore_changes on activation_policy, min_instance_count and manual_instance_count. The Cloud SQL start time is not documented → measure it in the deploy epic.
  i. Answer cache: its own RLS + FORCE; key adds the tenant's acl_version and the user's entitlement version; on a hit, re-run the citation verifier and recompute staleness flags; purge on document delete.
  j. Kafka on Confluent Basic has no in-cluster RBAC: event payloads are minimised (ids, hashes, redacted text only, never raw documents or prompts), separate API keys per service (producer/consumer), DLQ payloads redacted. Per-tenant topics rejected (topic and partition count); revisit with Confluent Standard RBAC at the trigger "real firm data".
  k. BigQuery: redacted text only; row access policies per tenant; authorised views for the dbt marts.
  l. Langfuse Cloud Hobby: traces carry metadata, hashes and redacted text, tagged by tenant; acceptable only for synthetic data. Trigger "real firm data" → self-host Langfuse v4 in the project (or drop third-party tracing).
  m. IdP tenant discovery: the SPA resolves the firm from the URL path `/t/<slug>` via a public `GET /v1/tenants/<slug>` that returns only {display name, idp_tenant_id}; served by a SECURITY DEFINER function reviewed in CI and the only such function allowed. The token's IdP tenant id maps to tenants.id before GUCs are set.
  n. dbt runs as `fa_dbt` (no owner rights); gold models are views with `security_invoker = true` or tables created by a post-hook that enables + forces RLS; CI asserts, for every table in tenant schemas, RLS enabled + forced + policies present; SECURITY DEFINER functions banned except the reviewed one in (m).
  o. OTel/DB instrumentation: SQL parameter capture off; no request bodies in logs or spans.
  p. Docling: HTML supported; EDGAR scope = fund summary prospectuses (497K HTML) for the first source; inline-XBRL tables tested in the ETL spike; chunk sizes measured with Voyage's tokenizer (count_tokens), not the HF tokenizer.
  q. Confluent Schema Registry region is fixed to the first cluster's region → create the cluster in us-central1 first. Essentials: 100 schemas free.
  r. Budget (recomputed, monthly): idle ≈ $40-55 (ALB $18.25, Cloud Armor ≈ $6-10 UNVERIFIED, Cloud SQL storage + IP ≈ $4-6, PSC endpoint, Confluent Basic ≈ $0-5, Artifact Registry/Secrets/GCS/logs ≈ $5, Kong/API/workers at 0); demo month (≈ 40 h up, ≈ 2,000 chats) ≈ $110-160 incl. LLM, evals and Valkey/Cloud SQL hours; always-on prod profile ≈ $300+ (out of budget, by design).
